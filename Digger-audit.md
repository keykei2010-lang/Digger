# Digger audit

**Audited 26 November 2026** · **Published branch** `main` · **Commit** `0f31f34b66af1f333b702005aece2466697850a8`. The audit covers the Windows desktop app, filesystem and sector recovery engines, previews, structural media repair, the local browser app, and distribution. It uses the published GitHub commit. [Audited source](https://github.com/keykei2010-lang/Digger/tree/0f31f34b66af1f333b702005aece2466697850a8)

**Release assessment.** Hold the Windows release. The packager accepted Sleuth Kit binaries that broke NTFS scanning. The media repair workflow published a substantially altered video despite decode errors. Some paths can also write to a disk while Digger is trying to recover its data.

**Evidence.** Entries marked **Reproduced** were exercised with synthetic fixtures or the built package. Entries marked **Verified at method level** were exercised directly in isolation. The remaining findings come from source review.

## Release blockers and data-loss risks

1. **Windows packaging can ship a broken NTFS engine. Reproduced.** The ZIP built and passed its integrity check, but the prepared `fls.exe` rejected the required `-Q` option under Wine, so the NTFS fixture scan failed. After compiling the three patched Sleuth Kit tools and using them in the test, the same fixture passed scanning, byte-range preview, and SHA-256 recovery. The packager copies prebuilt tools without checking that they support the required options. [Packager](https://github.com/keykei2010-lang/Digger/blob/0f31f34/package-windows.sh#L43) · [NTFS scanner](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L141)
2. **Scratch files can write to a live source disk.** Scratch directories, some preview copies, extraction diagnostics, and saved preferences can use system temp or `%LOCALAPPDATA%`. On the system drive, these writes can reuse free clusters that still contain deleted data. [Scratch directory](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L29) · [Extraction diagnostics](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L366) · [Preview copies](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2736) · [Preferences](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2881)
3. **Destination validation can miss a disk that is actively being scanned. Verified at method level.** During a mixed Recycle Bin scan, exporting only a retained item can bypass the active scan disk because validation derives its protected disks from selected entries. The media repair dialog also chooses its output independently of the active scan. [Destination validation](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2780) · [Media repair dialog](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1325)
4. **CSV export can overwrite the source image.** The report path validates the parent directory for live sources and opens the chosen filename in write mode. If the user confirms overwriting the image itself, there is no source-file identity check to stop it. An interrupted write can also truncate an existing report. [Report export](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2789)
5. **MP4 repair publishes incorrect frame counts and timing. Reproduced end to end.** The reconstruction treats individual H.264 slices as complete frames. A 24 fps clip with 36 frames and four slices per frame became 144 reported frames and stretched from 1.5 to 6 seconds. The app published the repaired copy after a single preview frame decoded. A full FFmpeg decode reported errors. [Frame reconstruction](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/mediaRepairCjs.cjs#L846) · [Publish check](https://github.com/keykei2010-lang/Digger/blob/0f31f34/media_repair.py#L44)
6. **AVI repair can discard valid footage. Reproduced at engine level.** The repair loop expects flat chunks in `movi`. It stops at a legal nested `LIST rec ` group and drops everything from there. A synthetic structure shrank from 68 to 24 bytes and lost its video payload. A clip with frames before the first nested group could still pass preview verification. [AVI repair](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/mediaRepairCjs.cjs#L1409)

## Discovery and recovery accuracy

7. **Lost-partition scans stop at the first unreadable block. Reproduced with a short-read fixture.** A short read or I/O error ends the search. Partitions beyond that area are never examined. A failed filesystem probe can also end the partition loop. [Boot-sector scan](https://github.com/keykei2010-lang/Digger/blob/0f31f34/partition_search.py#L9) · [Filesystem probe](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L102)
8. **Valid FAT partitions can be missed. Reproduced.** The lost-partition search relies on optional FAT type label text. Blanking the label in a FAT16 fixture preserved direct filesystem detection at the known offset, but lost-partition discovery missed it. [Signature search](https://github.com/keykei2010-lang/Digger/blob/0f31f34/partition_search.py#L4) · [FAT detection](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L112)
9. **4Kn image offsets are interpreted as 512-byte sectors.** Physical lost-partition mode rejects 4Kn devices. An image can pass the 512-byte length alignment check and then be probed at the wrong byte offsets. Indexed image scans have the same fixed offset assumption. [Input validation](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1400) · [Partition offsets](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L83)
10. **An allocated filename can be classified as deleted. Verified at method level.** The lost-partition parser handles allocated and deleted rows. A filename that literally ends in ` (deleted)` is stripped and marked deleted, so later allocation checks can reject a recoverable file. [Body-file parser](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L56)
11. **A partition-table timeout can look like an empty table.** The app kills `mmls` after 25 seconds, suppresses stderr, and parses remaining output without checking the exit status. Missing partitions can disappear without a diagnostic. [Partition-table reader](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L83)
12. **Overwritten FAT or exFAT payloads can go undetected.** Live validation checks allocation of the directory record and its recorded size. It does not check whether payload clusters were reused. A successful read can return the expected length with unrelated bytes. [Recovery evidence](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L326)
13. **Some recovery reads cannot be timed out or canceled.** Synchronous NTFS bitmap and `icat` reads can block. The latter is also used to read emptied-bin metadata. The UI declines normal close while saving, so a stalled device can leave the user without an in-app stop control. [Bitmap read](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L301) · [Extraction](https://github.com/keykei2010-lang/Digger/blob/0f31f34/ntfs_recovery.py#L366) · [Close behavior](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L3135)
14. **Sector error reporting can overstate or understate damage.** The catalog reports an error after a bulk read failure even when every individual retry succeeds. A validation read failure can instead drop a candidate silently. [Sector retries](https://github.com/keykei2010-lang/Digger/blob/0f31f34/catalog/photorec-catalog.patch#L297) · [Candidate validation](https://github.com/keykei2010-lang/Digger/blob/0f31f34/catalog/catalog_io.c#L97)
15. **“All file types” uses PhotoRec's default selection.** Some supported signatures are disabled by default and Digger supplies no overrides in this mode. [Catalog command](https://github.com/keykei2010-lang/Digger/blob/0f31f34/sector_catalog.py#L124) · [PhotoRec defaults](https://github.com/keykei2010-lang/Digger/blob/0f31f34/catalog/photorec-catalog.patch#L133)
16. **The movie filter varies between scan stages.** Indexed scanning accepts only `.mp4` and `.mov`. The PhotoRec `mov` family also covers formats such as 3GP and JP2. [Indexed filter](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1536) · [PhotoRec filter](https://github.com/keykei2010-lang/Digger/blob/0f31f34/sector_catalog.py#L124)
17. **Unpaired Recycle Bin payloads disappear under a drive-root filter. Reproduced.** An unmatched deleted `$R` payload appears in an all-bin scan but is suppressed under the root of its known drive. [Unpaired payload handling](https://github.com/keykei2010-lang/Digger/blob/0f31f34/recycle_bin.py#L128)
18. **Retained Recycle Bin failures can look like full coverage.** Inaccessible bins are silently skipped. A disappearing child during traversal can abandon the rest of a deleted directory. The app tracks emptied-bin failures separately. [Retained-bin traversal](https://github.com/keykei2010-lang/Digger/blob/0f31f34/recycle_bin.py#L76)
19. **Saved Volume Shadow Copy versions lose their snapshot identity.** Multiple versions of the same path receive the original name and numeric collision suffixes. The snapshot dates exist in the UI and optional CSV, but are absent from the saved filenames. [Snapshot results](https://github.com/keykei2010-lang/Digger/blob/0f31f34/shadow_versions.py#L73) · [Output naming](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L3007)

## Desktop, previews, and media repair

20. **“Continue with deep scan” discards results and selection.** It prepares a new scan. Starting it clears existing rows and checks, and scans the drive root without retaining the previous folder context. [Continue action](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L870) · [Scan reset](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1487)
21. **A folder deep scan can look empty while recovering candidates.** The pinned folder is also the initial active filter. Carved files are assigned to `Unknown folder` and are hidden until the filter is cleared. [Initial filter](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1505) · [Unknown-folder grouping](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1972)
22. **An old failure report can stay visible in later jobs.** Starting a new scan or completing a successful save does not clear the old report or hide its button. [Scan reset](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1470) · [Recovery completion](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L3066)
23. **Recovered results can keep stale thumbnails.** Save completion resets preview attempt and error flags but retains the cached bitmap. The thumbnail worker skips cached results, so the gallery can keep showing the pre-recovery preview. [Cache check](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2324) · [Save completion](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L3066)
24. **A verification exception can leave media repair permanently running.** Pillow's decompression-limit exception is outside the repair worker's catch list. If it occurs, no completion event clears the busy state, and Digger declines another repair or a normal close. [Repair worker](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1346) · [Close behavior](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L3135)
25. **Legal MP4 atoms are treated as damaged. Reproduced at engine level.** A size-zero atom can legally extend to EOF. The repair path marks it truncated and rewrites it. That path also uses a 32-bit size for extended-size atoms, risking an invalid header or wrap on large files. The mere presence of a `moov` box is also treated as evidence that the index is intact. [MP4 parsing and repair](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/mediaRepairCjs.cjs#L659)
26. **Streaming MP4 repair still has unbounded memory costs with respect to input size.** It allocates the declared `ftyp` length at once and retains per-sample arrays and generated index tables. Large or damaged files can exhaust memory. [File-type box allocation](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/mediaRepairCjs.cjs#L714) · [Index tables](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/mediaRepairCjs.cjs#L544)
27. **Preview read-ahead can exhaust the budget before fulfilling a small request. Reproduced at method level.** Buffer read-ahead counts against the explicit limit, so a small read can fail near that limit. Ordinary file previews bypass the explicit byte budget used for recovered candidates. [Extent reads](https://github.com/keykei2010-lang/Digger/blob/0f31f34/sector_catalog.py#L83) · [Preview dispatch](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2593)
28. **The video playback window can fail silently.** It has no Media Foundation callback for asynchronous open or codec failures. Closing an opened window returns success even if playback never began. [Player](https://github.com/keykei2010-lang/Digger/blob/0f31f34/catalog/player.c#L45)
29. **Large scans can repeatedly rebuild and sort all results on the UI thread.** Sorting or grouping can trigger a full rebuild for each incoming batch. Pagination caps the visible rows, while the computation still grows with the entire scan. [Batch updates](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L1733) · [Result sorting](https://github.com/keykei2010-lang/Digger/blob/0f31f34/desktop.py#L2390)

## Local browser app and distribution

30. **A rejected image leaves the previous image selected. Reproduced.** Selecting an empty image after a valid one shows an error but leaves Start enabled for the valid image. [Image selection](https://github.com/keykei2010-lang/Digger/blob/0f31f34/app.js#L39)
31. **Preview and download links fail for some filenames. Reproduced.** The client URL-encodes each path segment and the server compares the encoded text directly to the on-disk name. A result named `my photo.png` returned 404. [URL construction](https://github.com/keykei2010-lang/Digger/blob/0f31f34/app.js#L61) · [Server lookup](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L178)
32. **ZIP export can create duplicate member names. Reproduced.** Two rejected filenames from the same folder were both exported as `recovered-file`, leaving extractors to overwrite or prompt about indistinguishable names. [ZIP naming](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L257)
33. **Browser jobs retain images and output for the life of the server.** There is no expiration or delete operation. The upload space check makes no reservations across concurrent jobs. Export creates another on-disk copy and the browser materializes the full ZIP as a Blob. [Job storage](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L218) · [ZIP download](https://github.com/keykei2010-lang/Digger/blob/0f31f34/app.js#L206)
34. **The browser offers no upload cancellation, and large selections can fail on export.** Stop appears only after upload finishes. A selection with serialized IDs exceeding the server's 1 MiB request limit receives a generic “Invalid selection.” [Stop control](https://github.com/keykei2010-lang/Digger/blob/0f31f34/app.js#L52) · [Export limit](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L257)
35. **Loopback browser sessions share service access.** The session endpoint grants a single process-wide token. Status, previews, and downloads rely on knowing the job ID without requiring that token. This gives limited isolation on shared machines. [Session handling and reads](https://github.com/keykei2010-lang/Digger/blob/0f31f34/server.py#L148)
36. **Builds rely on independent, manually prepared inputs.** The Windows audit build required restoring the missing Node binary and PyAV wheel. The scripts do not verify every input or tie engine binaries to their sources. The Linux packager independently chooses prebuilt engines and archives a checkout's `HEAD`, which can differ from the shipped engine revision. [Windows inputs](https://github.com/keykei2010-lang/Digger/blob/0f31f34/package-windows.sh#L3) · [Linux source archive](https://github.com/keykei2010-lang/Digger/blob/0f31f34/package.sh#L52)
37. **Linux portability depends on the host loader and glibc.** The package invokes `/lib64/ld-linux-x86-64.so.2` and uses host glibc. The ZIP ran on the audit host. Compatibility with older or non-glibc distributions depends on their runtime. [Linux runtime packaging](https://github.com/keykei2010-lang/Digger/blob/0f31f34/package.sh#L18)
38. **The application license is ambiguous.** Digger lacks a top-level application license. The repository contains a vendored GPL repair module and distributes modified third-party engines. The application license and binary-to-source records need clarification before distribution. [Repository](https://github.com/keykei2010-lang/Digger/tree/0f31f34) · [Repair module provenance](https://github.com/keykei2010-lang/Digger/blob/0f31f34/repair/README.md)

## Verification and limits

- All six existing unit tests passed. Python source parsing and shell and JavaScript syntax checks passed.
- The Linux NTFS fixture recovery matched its expected SHA-256, `833d518b36e9b97849398241881ea06f37c70ecb2d7b1c6d2af78c44ea2cb973`. Synthetic FAT12, FAT16, FAT32, and exFAT images produced byte-for-byte deleted-file recoveries.
- The Linux package passed sample inspection, carving, individual download, and ZIP export. The Windows package built after supplying the missing prepared inputs and passed its archive integrity check.
- Under Wine, the Windows package passed PNG carving and recovery for three fixtures and decoded a video preview. Substituting locally built patched Sleuth Kit frontends allowed the Windows package to pass the NTFS fixture, including byte-range preview.
- Native Windows raw-device access, live FAT/exFAT behavior, and Volume Shadow Copy integration remain unverified. The refreshed Windows ZIP was tested with synthetic files under Wine. The audit used an isolated copy of the published source.

## Data Recovery Test priorities

1. Build or pin the patched Windows recovery engines and prove required options and recovery against fixtures inside the packaged ZIP.
2. Enforce the write guard across every active source disk, including scratch files, report export, preferences, and media repair.
3. Add media repair fixtures that check sample boundaries, frame count, duration, and full-stream decode before publishing a repaired copy.
